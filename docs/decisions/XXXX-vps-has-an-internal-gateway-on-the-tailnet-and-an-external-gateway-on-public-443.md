# ADR XXXX: vps has an internal Gateway on the tailnet and an external Gateway on public 443

Source: [issue #1482](https://github.com/corekraft/kore/issues/1482), under the platform v1 interview record [#1478](https://github.com/corekraft/kore/issues/1478) (decision 5 and the naming section).

Refines: [ADR 0142](0142-the-vps-environment-targets-the-persistent-k3s-node-as-a-managed-cluster.md) (the vps overlay has one Gateway, the placeholder domain `kore.internal` and no public ingress), [ADR 0085](0085-k3d-gateway-answers-through-a-node-port.md) (the overlay declares the Gateway's node port) and [ADR 0133](0133-the-platform-owns-the-gateway-its-listeners-and-its-certificate-charts-own-routes-only.md) (one shared Gateway).

## Context

The record decides two Gateways: an external one with a public listener and an internal one reachable on the tailnet only, internal by default and external an explicit per-app opt-in. Today the platform has one Gateway, `kore-gateway` in `kore-system`, named by every chart, route, spec and the platform DNS rewrite, and the environment schema has one `gateway` field.

On vps nothing publishes a Gateway: k3s runs with servicelb disabled (ADR 0141), so a Gateway Service has no address. The host firewall (`infra/hosts/vps/roles/network/files/nftables.conf`) filters only the input chain and accepts everything on `tailscale0`. Traffic that kube-proxy translates to a node port is forwarded, not delivered to the host, so that table does not filter it: a node port would be reachable on the public interface today. The repository is public, so neither the public nor the tailnet address may be committed (ADR 0142).

## Decision

- **Two Gateways, both agentgateway, in `kore-system`.** The internal Gateway keeps the name `kore-gateway`, so no chart, route or spec moves. The external Gateway is new, `kore-gateway-external`. The environment's `gateway` field becomes `gateways.internal` (required) and `gateways.external` (optional); local declares only the internal one. A record that says `gateway: external` in an environment with no external Gateway is refused by `kore validate`.
- **What rides which Gateway.** The internal Gateway carries every platform name (registry, databases, telemetry, portal, Keycloak, Argo CD) and every service by default. The external Gateway carries HTTPS-terminating listeners for the routes of services whose record opts in, and only routes of kind `HTTPRoute`: never TLS passthrough, TCP, a database, the registry, telemetry, or any platform name.
- **Domains.** `platform.domain` stays the public domain. A new optional `platform.internalDomain` is the internal one; when an environment declares no external Gateway it defaults to `platform.domain`, so local keeps `<service>.platform.kore.internal`, and vps sets `internal.<domain>` once the domain exists. A suborg's zones are `<suborg>.<domain>` and `<suborg>.<internalDomain>`. `internal` is a reserved name. The internal Gateway's own un-prefixed listener derives from the internal domain, and the external Gateway has no apex or un-prefixed listener at all.
- **Published as node ports.** Both Gateway Services are node ports declared in the vps overlay, as local declares its k3d node port. The Ansible `network` role, which already owns the `kore_host` table, maps the standard ports per address and drops traffic on every non-tailnet interface for every node port except the external Gateway's. The port table, kept in one Ansible variable file against which `kore validate` checks the overlay's node ports: public address, 80 (the certificate challenge and a redirect only) and 443 to the external Gateway; tailnet address, 443 to the internal Gateway, 53 UDP and TCP to the platform DNS (ADR XXXX, internal split DNS), and what the host already allows on `tailscale0`. The internal Gateway has no port 80. Nothing else is reachable from outside the host.
- **One host-address contract.** Ansible writes one k3s auto-deploy ConfigMap, `kore-host-addresses` in `kore-system`, holding the tailnet and public addresses it reads from host facts. The platform DNS answers from it, and the external Gateway's DNS target annotation is rendered from it; concept 5 (DNS and the domain) consumes the same ConfigMap and adds no second source. Neither address enters git or a log. `kore validate` and the `kore platform up` preflight refuse an environment that turns on `platform-dns` or `external-gateway` for vps while the host role has not published it.
- **Dark flag, last in the order.** `external-gateway` renders the external Gateway and is false in every overlay. It needs `service-listener-sets` and `acme-issuers`, and it cannot be proven before the domain is bought, so it is among the last flags of the vps all-on.
- **Before the domain exists** everything internal is built and live-proved on vps with `kore.internal` and the in-cluster CA: the two-Gateway code, publishing, split DNS and claims. Proofs verify against the in-cluster CA's public certificate fetched from the cluster, since clients cannot install the vps CA (`kore trust install` refuses it, ADR 0142). Browsers on the owner's devices are not supported until the domain flips and show a certificate warning. `kore validate` refuses an app record with `gateway: external` while `platform.domain` is the placeholder `kore.internal`, and the platform records no app on vps before the flip, so the domain changes with nothing to migrate and no deprecated alias (ADR 0132's alias is local only).
- **Proof from outside the host.** `kore-agents` is a VM behind the host's NAT, so a probe from it never travels the public path. The public-side negative checks run as a `workflow_dispatch` job on a GitHub-hosted runner, with the public address in an Actions secret that is never printed or committed: an internal name and every node port are refused on the public address, an unknown name on 443 is served nothing, port 80 answers only the redirect and a challenge path. The tailnet-side checks run from `kore-agents` over the tailnet. Both go into the one recorded outcome for `external-gateway`. The dispatchable job is a new workflow and a dependency of this decision.

## Consequences

- ADR 0142's statements that the cluster has no public ingress and that the name is tailnet-only by design no longer hold once `external-gateway` is on; the internal part still does.
- A change to either Gateway, its Service, its node port or the port table is a platform change, reviewed as one.
- A node port that is not in the table is a validation failure before any mutation. Closing the public node-port exposure is a host change that needs its own check-mode run and live proof, like any host change (ADR 0141, ADR 0077).
- Rate and size limits on the external Gateway, who may sign in to an external app, and whether a Gatekeeper outage may admit a route are not decided here; they are open owner questions.
- The database passthrough listener (ADR 0136) and the registry and telemetry names stay internal. Whether `database-routes` and `otlp-route` apply to vps at all is a proposed marking, not decided here.
