# ADR XXXX: Retained databases are backed up by a scheduled age-encrypted dump and restored only from the controller

Source: [issue #1481](https://github.com/corekraft/kore/issues/1481), grilled against the owner interview record [#1478](https://github.com/corekraft/kore/issues/1478) (decision 4: opt-in per database, encrypted to the existing age key, short retention, a pluggable S3-compatible target, an interim target labelled "mechanics proven, not off-host").

Refines [ADR 0029](0029-local-export-and-restore.md) (the export and restore of retained data), [ADR 0070](0070-recovery-objectives-and-offline-ops-checks.md) (scheduled backups were managed-only and `planned`) and [ADR 0074](0074-backup-freshness-row.md) (there was no scheduler). Builds on [ADR 0141](0141-the-vps-host-is-converged-by-an-ansible-playbook-in-the-repository.md) and [ADR 0142](0142-the-vps-environment-targets-the-persistent-k3s-node-as-a-managed-cluster.md).

Status is `proposed`. Items marked **open owner decision** below were answered "recommend yes" by the answerer in the owner's place but are not in the record, so they are not settled.

## Context

kore-vps holds retained databases on `local-path` volumes on one RAID1 pair, the same disks as the host, the k3s volume and the agents VM. Retention is not a backup ([ADR 0003](0003-separate-claims-and-retain-data.md)). Today `kore data export` (ADR 0029) is a manual, controller-side dump of one namespace into the gitignored `.kore/exports/`, and `infra/catalog/recovery.yaml` contradicts itself: `managed-postgresql` is `planned` with a recovery point of 15 minutes and a daily cron. The PostgreSQL composition renders one CloudNativePG `Cluster` per claim with no backup configuration.

The owner has no off-host storage yet. Decision 4 asks the mechanics to be built and drilled now against an interim target, and an app with data not to go public until backups are off-host.

## Decision

- **A scheduled logical dump, not continuous archiving.** An in-cluster job runs `pg_dump` against each backed-up CloudNativePG cluster, pipes it through `age` to public recipients, uploads the ciphertext and writes a digest manifest, reusing the ADR 0029 formats. The Barman Cloud plugin ([#1173](https://github.com/corekraft/kore/issues/1173)) is not used: it has no client-side age encryption (decision 4), it injects a sidecar and rolls every database pod, and the objective below does not need point-in-time recovery. WAL archiving stays a later expand if an app needs a smaller loss.
- **The recovery point is 24 hours.** `recovery.yaml` gets a vps objective with `rpoMinutes` 1440 and a daily schedule outside the Sunday reboot window; the 15-minute line that contradicted its own cron is replaced.
- **Retention is short and a typed overlay value.** The newest N daily backups per database are kept and nothing older. N is **14** in this draft: **open owner decision** (bounds how long deleted personal data stays in a backup).
- **Opt-in per database, platform databases always.** The `backup` field of the spec file (reserved by the app model) sits on each database entry as `true` or `false`, default `false`, and silence is never an error. `kore platform status` names every database with backup off as unprotected. Databases the platform owns (Keycloak and any later one) are always backed up.
- **v1 covers PostgreSQL and OpenBao only.** App namespaces admit no PersistentVolumeClaim except those CloudNativePG owns (audit first, [ADR 0072](0072-constraint-promotion-procedure.md)), so no data class exists that v1 cannot restore. Velero stays a paused watch item ([#1231](https://github.com/corekraft/kore/issues/1231)).
- **The target is typed overlay config.** The vps overlay declares `backup.target`: endpoint, bucket, region, path style, an optional CA bundle, a credentials reference and a kind, `interim` or `off-host`. The kind is the owner's declaration; `kore validate` refuses `off-host` for a cluster-internal name or an address of the box or its VMs. The credentials are platform secrets encrypted with sops to the vps recipient and applied by `kore` through stdin; they are not held in OpenBao, which is itself backed up to this target.
- **Only public recipients on the box.** The job holds the public recipients and never an identity. Nothing in the cluster can decrypt a backup.
- **The box can write but not delete.** The credential the jobs hold creates objects and cannot delete or overwrite them. Retention is enforced by the target (object lock or a lifecycle rule) or, where the target cannot, by a prune command run from the controller with a separate delete credential held only there. Whether SeaweedFS object lock does this is to be confirmed in the drill.
- **Restore is controller-run only.** `kore data restore --environment vps --from <object in the target>` pulls the object with the controller's read credential, decrypts locally with the identity (age reads the key, `kore` never does), and streams into the CloudNativePG primary through `kubectl exec psql`. A non-empty database is refused without `--overwrite-data --yes`, the data-destruction second opt-in of ADR 0003 and ADR 0029.
- **A backup before every migration.** A release that carries any migration gets an on-demand backup as its first PreSync hook, ahead of the shadow run and the real migration, and the release is refused when that backup fails.
- **The shadow database comes from the live primary, not from a backup.** A dump piped straight into a scratch database, never stored, so no hook in the cluster ever decrypts a backup. This words the shadow migration of the app delivery decisions as "runs on a copy of the data" (owner, [#1485](https://github.com/corekraft/kore/issues/1485), answer 8), not "restores the latest backup".
- **What restorable means.** A database's newest backup is restorable when its manifest digest and size match the object in the target, it is under 24 hours old, and the mechanism has a recorded passing restore drill within the last **30 days** (**open owner decision**: the 30). A contract release (app delivery decisions, owner answer 8 on #1485) is refused at the record bump otherwise.
- **One record of freshness.** The job writes the last-success manifest metadata (database, time, digest, size, target kind) into a ConfigMap. The `backups` row of `kore platform status`, the contract check and the external-Gateway check read it with `kubectl` and never decrypt. The row stays audit-only for the status exit code and the admission gate (ADR 0074); the contract and Gateway checks are separate gates at the record bump.
- **Backup requires Retain.** `kore validate` refuses `backup: true` on a `Delete` claim, since a claim declared disposable cannot also be protected. A `Retain` database with backup off is allowed and reported unprotected. Platform databases are `Retain` and always backed up.
- **A third role and a replica read.** Each CloudNativePG cluster gets a generated `backup` role with `pg_read_all_data` and no write, beside the DDL and DML roles. The dump reads the replica service (`-ro`) when the cluster has two instances (standard class) and the primary when it has one (development class); two instances are availability, never a backup.
- **A dump keeps ownership and grants.** A restore needs the DDL, DML and backup roles to exist on the fresh cluster under the same names; the composition recreates them with new generated passwords and the workloads read the new Secrets, so no password is in any backup. The restore drill proves the roles exist before the load.
- **One pinned, signed backup image, distroless.** The job image is built by the release pipeline, signed, copied to the mirror by digest and admitted like any platform image. [ADR 0116](0116-application-runtime-images-are-distroless-builder-stages-can-be-anything.md) says every runtime image Kore builds is distroless, so there is no exception: the runtime stage is a distroless base that carries the libraries `pg_dump` needs (not the static variant), with `pg_dump` and its libraries copied from a builder stage, and with no shell the pipeline is one entrypoint program that starts `pg_dump` and streams it through `age` to the upload. `pg_dump` is the newest PostgreSQL major in use, which dumps older servers.
- **Layout and manifest.** One prefix per environment and database, `<environment>/<namespace>/<cluster>/<database>/<UTC timestamp>.dump.age`, with `<UTC timestamp>.manifest.json` beside it. The manifest is the ADR 0029 manifest extended with the target kind, the recipient list, the dump tool version and the PostgreSQL major, so a restore refuses a mismatched major before it decrypts. The OpenBao snapshot and any other copy use the same shape under their own prefixes.
- **One dump at a time.** Backup and snapshot jobs are serialized across the cluster (concurrency policy `Forbid`, one queue per environment). Every job pod declares CPU and memory requests with a memory limit equal to the request, and the platform reserve of the capacity decisions includes the largest backup pod, so a backup cannot starve an app or the registry.
- **Commands.** `kore data backup --environment vps [--service s]` runs the job on demand and waits for its manifest. `kore data restore` takes the target as a source. `kore data export` stays as ADR 0029 for a manual extra copy to the controller disk and counts for no gate. All offer `--json`.
- **Validate before touching a cluster.** `kore validate` refuses: a record with backup on while the overlay has no target; a target with a missing or placeholder recipient in `.sops.yaml`; an `off-host` kind on an internal endpoint; a stateful component with no `recovery.yaml` objective; the `database-backups` flag on without a target; and a service with data set to the external Gateway while the kind is `interim`. It reads files only.
- **Two gate facts, one enforcement point elsewhere.** This decision publishes two facts: the target kind, rendered from the overlay into a ConfigMap, and whether a service has data (a database claim or a declared secret name; the definition is an **open owner decision**). The Gateway decisions own the enforcement point, in two layers like capacity: a deterministic eval at the record bump and an admission constraint on the external route, audit first ([ADR 0072](0072-constraint-promotion-procedure.md)).
- **Data removal takes a final backup.** Any removal of data on vps (the `--purge-data` flag of `kore platform destroy` and the data-removal command the app model reserves) takes a final on-demand backup first, prints where it is, and never deletes backups. They age out by retention, which is the bound on how long purged personal data survives.
- **Destroy is refused without a restorable backup.** `kore platform destroy --environment vps` refuses while any retained database has no restorable backup, unless `--purge-data` is given, which takes the final backup first. This is ADR 0003 and ADR 0029 applied to a managed environment with the freshness record in place of the local export.
- **A backup before a platform rollout.** A rollout run whose chart or image lock changes CloudNativePG, the PostgreSQL composition, OpenBao or the k3s version refuses to start unless every backed-up database and the OpenBao snapshot have a restorable backup under 24 hours old, and takes an on-demand one first when they do not. A CRD-changing upgrade stays expand-contract and forward-only.
- **Alerts.** A failed or missed job (no success within the recovery point plus one hour) and an unreadable target raise notify-only alerts through the ADR 0128 path, from recording rules owned by one chart and not by the job; the address comes from the run-time environment and is never committed. They never gate admission.
- **OpenBao snapshots.** A second job takes a daily Raft snapshot through a Kubernetes-auth role limited to the snapshot path, encrypts it to the same recipients, writes it to the same target under the same retention and the same write-only credential. The recovery point for secret values is the same 24 hours. The seal key and recovery shares are custody items, not data.
- **Dark launch.** Two flags, each with its own live outcome and a `requires` in the flag manifest: `database-backups` (the job, the target config and the freshness record) and `openbao-snapshots` (requires the OpenBao provider flag and `database-backups`). Both are off in every overlay; an interim target counts as proven mechanics only.

## Consequences

- Nearly every external service waits for the off-host target, because "an app with data" includes a service that declares any secret name (**open owner decision**: that definition is the grilling's extension of decision 4). The wait is the point of decision 4.
- A scheduler now exists for vps. The local profile still has none; ADR 0029, 0070 and 0074 each need a refinement note pointing here.
- The dump passes through a pod rather than the controller, which ADR 0029 said was acceptable locally and not for a managed environment.
- A second recovery recipient, the placement of the interim target and the recovery kit are the owner's and are parked in the summary on #1481; nothing here depends on their answers.
