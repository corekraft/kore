# Trust Roots, Certificate and Secret Rotation, and Identity Incidents

Every trust root the local platform has, who owns it, and how to rotate it.
Commands are written as `kore ...` (see the [operator guide](../guides/operator.md)).

## Trust roots

| Root                                | Owner and location                                                                                                                                             | Lifetime                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Image signing key (local)           | `kore-system/kore-local-signing-key` Secret; public half in `cosign-system/kore-local-signing-pub`                                                             | the cluster ([signing and keys](signing-and-keys.md))  |
| Release signing identity (managed)  | `trust.subjects` in the environment's `image-policy` values                                                                                                    | per release tag                                        |
| Registry CA and serving certificate | cert-manager objects in `kore-registry` (`oci-registry-ca`, `oci-registry-tls`); public CA copied to `cosign-system/kore-registry-ca` and the node's `certs.d` | ten years (`tls.duration` in the `oci-registry` chart) |
| Gateway certificate (local)         | cert-manager `Certificate/kore-local`, issued by the local ClusterIssuer from the mkcert CA                                                                    | cert-manager defaults                                  |
| mkcert CA (host)                    | installed by `kore trust install --environment local` into the host trust store                                                                                | mkcert default; removed with `mkcert -uninstall`       |
| Registry push and read credentials  | `kore-registry/oci-registry-credentials` and `oci-registry-auth`; pull Secret `kore-registry-read` per enrolled namespace                                      | until rotated                                          |
| SOPS age recipient                  | `.sops.yaml`; the identity stays on the developer's machine                                                                                                    | until changed                                          |
| Workload identity                   | Kubernetes ServiceAccounts mapped to Istio SPIFFE principals                                                                                                   | per ServiceAccount                                     |

## Registry credentials

`kore registry rotate-credentials --environment local --yes` replaces both
passwords and every enrolled pull Secret without a window where admission cannot
read signatures; it is resumable
([ADR 0055](../decisions/0055-registry-credential-rotation.md)). It refuses an
external registry, whose credentials belong to its provider.

## Registry certificate and CA

The certificate is valid for ten years and the proxy reads it at start, so
rotation is a deliberate act ([ADR 0058](../decisions/0058-registry-transport-tls.md)).
**Gap:** no `kore` command rotates it. The documented sequence is: delete the
`oci-registry-tls` Secret (and `oci-registry-ca` to replace the CA) in
`kore-registry`, run `kore local up --environment local` (which reissues,
redistributes the CA to the ConfigMap and the node, and reapplies trust), then
restart the proxy with `kubectl --context kore-local --namespace kore-registry
rollout restart deployment/oci-registry`. `kore platform status` reports a
degraded `registry-trust` row while the CA is missing, which keeps the
admission gate closed.

## Gateway certificate and host CA

cert-manager renews `Certificate/kore-local` itself. To replace the host CA,
run `mkcert -uninstall` and `mkcert -install` (outside Kore), delete the
`kore-local-tls` Secret, and rerun `kore local up --environment local`; then
`kore trust install --environment local` re-trusts the CA on the host.
**Gap:** Kore does not test a CA replacement; it only installs the mkcert CA
before the Gateway is configured.

## Application secrets

Secrets reach applications through External Secrets from SOPS-encrypted
documents; plaintext never touches disk or git ([ADR 0009](../decisions/0009-encrypted-secrets-through-external-secrets.md),
[`infra/environments/local/secrets/README.md`](../../infra/environments/local/secrets/README.md)).

- **Reference API token:** generated by `kore local up`, stored with owner-only
  permissions at `.kore/state/reference-api-token`. The cluster's source Secret is
  created once and no other checkout overwrites it ([ADR 0075](../decisions/0075-token-source-has-one-owner-and-rotation-rolls-consumers.md)).
  To rotate, run `kore secrets sync --environment local --rotate --yes`, then
  `kore local up --environment local` so the API pods restart onto the new
  value.
- **Other secrets:** edit the `*.enc.yaml` document with `sops`, then run
  `kore secrets sync --environment local`.
- **SOPS age recipient:** `.sops.yaml` holds the recipient. Replace it, re-encrypt
  each document with `sops updatekeys`, and rerun `kore secrets sync`. **Gap:**
  no `kore` command re-encrypts documents or rotates the recipient, and
  `kore data export` refuses the placeholder recipient
  `AGE-RECIPIENT-MUST-BE-CONFIGURED`.

## Workload identity incident response

A ServiceAccount token or identity is suspected stolen:

1. **Contain.** `kore app down <name> --environment local` removes only the
   workload release (rerunning is safe; the resources release and data are
   kept). Its ServiceAccount is part of the workload chart, so it is deleted
   with it.
2. **Invalidate.** `kore app up <name> --environment local` creates a new
   ServiceAccount, so the old identity's tokens stop working and Istio
   authorization bound to the old principal stops matching. For a quicker
   cut-off, `kubectl --context kore-local --namespace <ns> delete
serviceaccount <name>` before the redeploy.
3. **Review.** Gatekeeper's `KoreWorkloadIdentity` constraint audits workloads
   on the namespace default ServiceAccount; read its violations with
   `kubectl --context kore-local get koreworkloadidentity kore-workload-identity
--output yaml`. The OPA authorizer decisions are logged with masked fields.
4. **Confirm.** `kore app status <name> --environment local` reports the
   release and whether admission is degraded.

**Gap:** no `kore` command revokes a single identity or lists the principals a
ServiceAccount used; and the SPIFFE principal OPA receives is not yet verified
live (plan Step 9).
